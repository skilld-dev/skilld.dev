## Outcomes

Worked the actions in the same session. Nothing below is deployed, and production was not mutated.

**1. Root-caused and fixed locally.** It is a write, not a read, which is why the 2026-08-10 read-side chunk changed nothing. `db.batch(writes)`{lang="ts"} at the end of each slice in `syncRepo` binds `rendered_raw` and `rendered_html` for every admitted skill at once. `SKILL_SLICE_SIZE` bounds that batch at 50 skills, and skill content is unbounded, so the batch tracks content rather than count. `garrytan/gstack` holds 58 skills with 11,140,589 characters of rendered HTML, averaging 192 KB each, so one slice binds about 12.4M characters and serialized to 48,516,427 bytes.

The fix bounds the batch by payload instead of by count: `weighWrite` binds and measures a statement in one step so an unmeasured write cannot enter the queue, `planWriteBatches` splits into contiguous groups under an 8,000,000 character budget, and `runBoundedBatch` merges results back in input order so the change-count accounting still addresses the right rows. Splitting is safe because every write in the slice is already idempotent. Five cases in `test/unit/sync-repo-d1-bounds.test.ts` cover it, including a reconstruction of the failing gstack slice against a 32 MiB stub ceiling. Full suite: 750 passed, 129 files. Lint clean.

**2. Root-caused, and not ours to fix here.** `nuxt-ai-ready/dist/runtime/server/db/shared.js:201` upserts with `ON CONFLICT(route)`{lang="ts"} while the table also holds a UNIQUE index on `route_key`. `route_key` strips the leading slash, so `""` and `"/"` both key to `index`. Production holds one row at `route = ''` with `last_seen_at` NULL, and every tick then tries to write the home page as `route = '/'`, misses the `route` conflict target, and hits the `route_key` index. Two fixes: upstream, normalise the route or change the conflict target; locally, delete the one malformed row so the canonical `/` row can be written. The local one mutates production, so it needs your go-ahead.

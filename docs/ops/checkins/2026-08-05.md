Root-caused 2026-08-05 with `wrangler d1 insights skilld-db`, which reaches historical query statistics the observability telemetry API refuses for the wrangler OAuth token. The burst had a background cause beyond the uncached hot path. Ranked by total D1 time:

| Total ms | Runs | Avg ms | Avg rows read | Query |
| ---: | ---: | ---: | ---: | --- |
| 1,189,148 | 11,576 | 102.7 | 6,793 | `skills` joined to `repos`, filtered by `json_each(?)`{lang="ts"} |
| 732,532 | 1,739 | 421.2 | 430,099 | `ai-ready:cron` status counters |

The two `ai_ready_pages` counters dominated, against a table of 143,470 rows, on a five-minute cron. A caveat on those totals. `wrangler d1 insights` ignores `--time-period`: `1d`, `3d` and `7d` return byte-identical output, so the span behind the `Total ms` and `Runs` columns is whatever D1 retains and cannot be stated. This was assumed to be seven days when first written and corrected the same day. The per-run averages, the ranking, and every before-and-after figure below are unaffected, because those came from direct `d1 execute` calls reporting their own `rows_read` and `duration`.

The cause was index selectivity: the table carries single-column indexes on `indexed` and on `is_error`, and the planner chose `idx_ai_ready_pages_is_error` for `WHERE indexed = ? AND is_error = 0`. Every row but 80 is `is_error = 0`, so that index matched nearly everything and `indexed` was filtered row by row. Production holds 143,390 rows at `indexed = 1, is_error = 0`, 80 at `indexed = 1, is_error = 1`, and none at `indexed = 0`, so the pending counter read the whole table every five minutes to return zero.

Migration `0091` adds the composite index over `indexed` and `is_error`. Measured on production after applying: the pending counter went from a 143,319-row scan to `SEARCH ... USING COVERING INDEX`, reading 0 rows in 0.22ms, and the combined status query from 430,099 rows to 286,861.

The remaining 286,861 splits into an unavoidable `COUNT(*)`{lang="ts"} over 143,470 rows and the `indexnow_pending` subquery, which still scans despite a partial index matching its predicate exactly and holding only 171 entries. The planner has no size estimate for that index, so `ANALYZE` is the likely fix. Left undone deliberately: it is a second production mutation and belongs in its own pass.

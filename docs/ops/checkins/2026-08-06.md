## Fixed this session

Two of the five proposed actions are implemented, tested and awaiting deploy. Production was not touched.

- **The probe now reports recurrences** (`scripts/tools/sentry-observability.mjs`, `scripts/tools/daily-checkin-data.mjs`). The query moved from `firstSeen:>{since}` to `lastSeen:>{since}`, and issues are split into `newIssues` and `recurringIssues` by comparing `firstSeen` against the window start. The page limit rose from 10 to 25 with a `truncatedAtLimit` flag, because recurrences now share the page and a silent cap reads as a complete list. Verified against live Sentry on this exact window: the old query returned 0 issues, the new one returns **7 recurring**, including two the manual investigation missed, `SKILLD-2` (D1 overload, first seen 2026-07-23, 10 events) and `SKILLD-D` (`Could not fetch SKILL.md`, 4 events, still firing at 01:45Z). So the D1 overload family is six ids, not five.
- **An unreadable blob no longer fails a whole repository** (`layers/registry/server/utils/github-client.ts`, `layers/registry/server/utils/sync-repo.ts`). `getBlobsBatch` now asks [GitHub](https://github.com) for `isBinary` alongside `text`, which is the only way to tell a blob that is missing from one it refuses to hand back, and returns the unreadable paths separately. `syncRepo` treats only a genuinely absent blob as a partial batch; an unreadable one is skipped, counted in a new `skillsUnreadable` stat, and its already-indexed row is protected from the disappeared-skill sweep, because "we could not read it" is not "the author deleted it".

Verification: 713 tests pass, typecheck clean, lint clean on every changed file. Ten tests are new, three of them written against the `lev-os/agents` failure before the fix existed. The two `modules/mdxg` spec files that fail to spawn a worker in the full run are the flake documented in `vitest.config.ts`; they pass in isolation, before and after these changes.

Measured, read-only, against the real repository: `lev-os/agents` has exactly **1** unreadable file out of 2,853.

**Correction to an earlier claim in this report.** I first wrote that this fix unblocks the largest ingest available. It does not, and the admission gate is the reason. The repo has 18 stars, no editorial review, no trust override, is not official and is not owner-verified, so `hasPrimaryTrustSignal` is false for every one of its skills and `scoreSkillIndexability` returns `indexable: false` regardless of score. With nothing admitted, `syncRepo` records `rejected: trust_inputs_insufficient`, which `discoveryOutcomeFromSyncStats` already treats as terminal. The real value of the fix is therefore that the repository reaches a decision at all: today it fails on a blob read and retries forever, after the fix it is judged once and rejected on the indexable-only policy, which is the outcome that policy intends. A personal dotfiles dump of 2,853 skills is precisely the long tail the catalog retirement culled.

## Investigation: the rolled-back deploy

Evidence from run 30365494042:

- The smoke failed only on the leaderboard asset-coherence stage, on `/_nuxt/v2/sZflUEPt.js`, `/_nuxt/v2/Bp78ZnTt.js`, and `/_nuxt/v2/4_hXFMXe.js`. All nine page expectations passed, and the post-rollback recovery smoke passed on the first attempt.
- Wrangler uploaded all three files in that same run ("Uploaded 507 of 507 assets", each of the three listed by name), so this was not a missing upload.
- The three chunks correspond to `SkillCard.vue` and `skills/leaderboard.vue`, the only components `bd41dde` changed.
- Skew protection worked: it stored 522 assets and restored 3 prior releases.
- Version 502623f9 went live at 13:54:42Z and the rollback was issued at 13:55:59Z, so the assets 404ed for roughly 77 seconds while the site served HTML referencing them. Real users on the leaderboard in that window would have failed to hydrate.
- Reproducing the same check against current production passes: the leaderboard references 107 assets and every one returns 200.

The check therefore caught a genuine rollout incoherence rather than misfiring, and it had passed on the four deploys immediately before this one. The design flaw is the retry budget. `nuxt.config.ts` puts `cloudflare-cdn-cache-control: max-age=60` on `/_nuxt/v2/**`, so a 404 observed during rollout is pinned at the edge for 60 seconds, while the smoke's budget is 12 attempts at 5 seconds, which is also 60 seconds. The existing tests covered the smoke *creating* a poisoned entry (the cache-busted readiness probe) but not an entry poisoned before the smoke began, which is what happened here.

## Fixes applied this pass

1. `scripts/lib/production-smoke.ts` now outwaits the CDN TTL. When the cache-busted readiness probe proves origin holds every asset, a clean-URL 404 is a stale edge entry, so the loop waits `cdnCacheTtlMs` (60s, matching the routeRule) instead of the 5s retry delay, bounded to two such waits. Regression test: "outwaits a CDN-cached 404 that predates the smoke".
2. `shared/server/cache.ts` adds `writeCache`, a best-effort cache write. All 15 awaited `useStorage('cache').setItem` call sites across `layers/` and `server/` now route through it, so a KV 429 costs a cache entry instead of the user's page. A static test keeps bare `setItem` calls from returning.
3. `layers/registry/app/utils/repo-profile.ts` adds `selectRepoSkills` and `selectRepoInfo`, which tolerate a profile whose `skills` or `repos` array is absent. The `/gh/[owner]/[repo]` page uses them in place of the unguarded `profile.skills.filter` and `repoProfile.value.repos.find`.

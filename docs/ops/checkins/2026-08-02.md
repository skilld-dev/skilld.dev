## Investigation: the rolled-back deploy

Evidence from run 30365494042:

- The smoke failed only on the leaderboard asset-coherence stage, on `/_nuxt/v2/sZflUEPt.js`, `/_nuxt/v2/Bp78ZnTt.js`, and `/_nuxt/v2/4_hXFMXe.js`. All nine page expectations passed, and the post-rollback recovery smoke passed on the first attempt.
- Wrangler uploaded all three files in that same run ("Uploaded 507 of 507 assets", each of the three listed by name), so this was not a missing upload.
- The three chunks correspond to `SkillCard.vue` and `skills/leaderboard.vue`, the only components `bd41dde` changed.
- Skew protection worked: it stored 522 assets and restored 3 prior releases.
- Version 502623f9 went live at 13:54:42Z and the rollback was issued at 13:55:59Z, so the assets 404ed for roughly 77 seconds while the site served HTML referencing them. Real users on the leaderboard in that window would have failed to hydrate.
- Reproducing the same check against current production passes: the leaderboard references 107 assets and every one returns 200.

The check therefore caught a genuine rollout incoherence rather than misfiring, and it had passed on the four deploys immediately before this one. The design flaw is the retry budget, and it has two halves. The first is edge caching. `nuxt.config.ts` puts `cloudflare-cdn-cache-control: max-age=60` on `/_nuxt/v2/**`, so a 404 observed during rollout is pinned at the edge for 60 seconds, while the smoke's budget is 12 attempts at 5 seconds, which is also 60 seconds. The existing tests covered the smoke *creating* a poisoned entry (the cache-busted readiness probe) but not an entry poisoned before the smoke began, which is what happened here.

The second half surfaced only after that fix shipped. `e518db8`, a docs-only commit carrying it, failed the same way an hour later on five chunks, and it burned all 12 attempts including the cache-busted probe. A probe that bypasses the edge cache and still 404s means origin itself lacked the asset, so edge caching cannot be the whole story. Assets are served by the per-version ASSETS binding before any request reaches the Worker (`server/runtime/cloudflare-public-assets.ts` deliberately leaves Nitro's asset table empty), so during a rollout the HTML can come from the new version while an asset request still lands on the old one, which has never heard of that chunk. Rolling back does not shorten the window, because the rollback is itself another version switch.

The flake rate is close to even: three consecutive deploys of near-identical code went pass (`3ab8ea5`), fail (`e518db8`), pass (`a1b4f32`). Asset coherence now gets its own 48-attempt budget, roughly 4 minutes, while the page checks keep their 12. The gate keeps its meaning: assets still incoherent after 4 minutes are a real fault worth rolling back for.

## Investigation: embedding parity

The audit's eligibility predicate and the producer's are identical (`broken_since IS NULL`, `current_sha IS NOT NULL`, `rendered_raw IS NOT NULL`, `rendered_status = 'ok'`, `seo_indexable = 1`), compared line by line in `layers/registry/server/utils/embedding-parity.ts:5` against `layers/registry/server/utils/ai-generation-work.ts:70`. Selection is sound. Throughput is the problem, in three compounding ways:

1. **The cap sits below the ingest rate.** `runtimeGenerationLimits` (`ai-generation-work.ts:9`) clamps embeddings to 20 per run, and `ai-generate-submit` runs at `15 * * * *`, so the ceiling is 480 per day. The window ingested about 504 per day. The backlog can only grow while ingest continues at that rate.
2. **New skills sort last.** Selection ends `ORDER BY s.installs DESC`, and crawler-ingested skills enter with `installs = 0`, so they are structurally the last to be served from the 20 available slots. This changes which skills wait, not how many get done.

A third mechanism looked likely from the code and does not survive the production data. `embedding_attempts` is write-only, so a repeatedly failing skill would keep satisfying the `NOT EXISTS` guard and re-consume a slot every hour. Production says that is not happening. Grouping `embedding_attempts` by state:

| State | Total | Last 7 days | Last 24h | Most recent |
| --- | ---: | ---: | ---: | --- |
| completed | 7,004 | 3,196 | 480 | 2026-08-03 03:15Z |
| rejected | 2,455 | 0 | 0 | 2026-07-24 05:16Z |
| provider_failed | 121 | 116 | 0 | 2026-07-27 04:19Z |
| started | 6 | 3 | 0 | 2026-07-29 16:15Z |

480 completions in 24 hours is exactly 20 per hour times 24, so the producer is saturated at its cap and every slot did real work. All 2,455 rejections carry a single error code, `malformed_acknowledgement`, and all of them fall between 2026-07-23 and 2026-07-24, which is the incident the ledger already closed on 2026-07-25. Nothing has been rejected since. The 127 skills behind those rejections are not being retried today.

`vector_succeeded_marker_failed` has zero rows, so it is not the source of the 53 orphans either.

The real picture is simpler than the code review suggested: the pipeline is healthy and running flat out, and drift is the arithmetic of 480 embedded per day against roughly 227 newly eligible per day, a net drain of about 253, which matches the observed 425 to 172. It converges on its own once ingest slows. Raising the cap only buys faster convergence.

`ai_submitted` does not measure this pipeline. It counts open Anthropic batch rows in `ai_batches` (`scripts/tools/daily-checkin-data.mjs:186`), which embeddings never touch, and it is 0 by construction because `HAIKU_GENERATION_PAUSED = true` (the deindexing kill switch) prevents any batch row from being created. Reading it as "no embedding work happened" was wrong. The real signals are `embedding_attempts` grouped by `state` and the `embeddingsWritten` / `embeddingsProviderFailed` / `embeddingsMarkerFailed` counters in `runSubmit`, which are only `console.warn`ed and never persisted.

## Fixes applied this pass

1. `scripts/lib/production-smoke.ts` now outwaits the CDN TTL. When the cache-busted readiness probe proves origin holds every asset, a clean-URL 404 is a stale edge entry, so the loop waits `cdnCacheTtlMs` (60s, matching the routeRule) instead of the 5s retry delay, bounded to two such waits. Regression test: "outwaits a CDN-cached 404 that predates the smoke".
2. `shared/server/cache.ts` adds `writeCache`, a best-effort cache write. All 15 awaited `useStorage('cache').setItem` call sites across `layers/` and `server/` now route through it, so a KV 429 costs a cache entry instead of the user's page. A static test keeps bare `setItem` calls from returning.
3. `layers/registry/app/utils/repo-profile.ts` adds `selectRepoSkills` and `selectRepoInfo`, which tolerate a profile whose `skills` or `repos` array is absent. The `/gh/[owner]/[repo]` page uses them in place of the unguarded `profile.skills.filter` and `repoProfile.value.repos.find`.
4. Asset coherence gets its own 48-attempt budget, separate from the 12 the page checks use, so the smoke outlasts a version-propagation window instead of rolling back through it. Regression test: "keeps probing assets while a new version propagates past the page budget".
5. `discoveryOutcomeFromSyncStats` now classifies `repo fetch 404`, `repo fetch 410` and `tree_truncated` as rejections rather than retryable failures, which is what produced most of the nightly "97 discovery candidates exhausted automatic retries" reason. 401 stays retryable on purpose, since it means our credentials rather than their repository.
6. The check-in collector records `embeddings_completed`, `embeddings_failed` and `embeddings_stuck` from `embedding_attempts`. The first run reports 80 completed, 0 failed and 6 stuck, which is the signal that was missing when `ai_submitted` reading 0 sent this pass down the wrong path.

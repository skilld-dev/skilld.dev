## Broken

### 1. Repository sync cannot finish a repository over 200 skill files

`registry/repo-maintenance` recorded 548 `Exhausted retries (dead-letter queue)`{lang="ts"}
failures from 2026-08-12T02:02Z through 2026-08-16T04:04Z, still firing at the
probe. It is the whole of the 623 failed jobs in the window, against 18 in the
prior archive.

Root cause, read from production rather than inferred. Every dead-lettering
repository sits at `repo_sync_progress.next_offset = 200` exactly:

| Repository | next_offset | total_skills |
| --- | ---: | ---: |
| `posthog/posthog` | 200 | 236 |
| `shipshitdev/library` | 200 | 375 |
| `github/awesome-copilot` | 200 | 425 |
| `sickn33/antigravity-awesome-skills` | 200 | 6,341 |
| `jeremylongshore/claude-code-plugins-plus` | 200 | 5,598 |
| `affaan-m/everything-claude-code` | 200 | 897 |

`SKILL_SLICE_SIZE` is 50, so 200 is four slices. The handler releases the queue
message back after each slice, and `releaseDurableJob` is followed by
`message.retry()`{lang="ts"}. The `skilld-repo-sync` consumer set `max_retries: 3`, so a
message gets four deliveries before [Cloudflare](https://cloudflare.com) routes it to the dead-letter
queue. Progress was spending the failure budget, so the sync stopped at exactly
four slices regardless of repository size, and the hourly tick re-enqueued the
same doomed job forever.

`jobs.retry_reasons` confirms it: every entry is `controlled release` with
`delaySeconds: 1`, `last_error` is null, and the final entry is `dlq-arrival`.
Nothing failed.

The same setting caused the observability gap this ledger row has carried since
2026-08-05. The job definition's own failure cap is `tries: 5`, checked against
`jobs.attempts` in the runtime's catch path. With the queue allowing only four
deliveries, a genuinely throwing job reached the DLQ before it reached its fifth
attempt, so `failed_jobs.exception` recorded the DLQ headline instead of the real
error.

Fixed in this pass, in three parts. All shipped in `23aecea`.

**The delivery budget.** `max_retries` raised from 3 to 100 on
`skilld-repo-sync` and `skilld-repo-review-sync`, with the invariant written into
`wrangler.jsonc`. This does not weaken failure handling, because `tries: 5`
terminates a failing job.

**The per-invocation cap.** `SKILL_PATHS_PER_INVOCATION` was pinned to
`SKILL_SLICE_SIZE`, which spent one queue delivery per 50 files. Those two
constants bound different things. `syncRepo` walks its chunk in
`SKILL_SLICE_SIZE` slices and releases each slice's content before the next, so
the memory bound belongs to the inner slice and does not grow with the outer cap.
The repo-wide tree listing and existing-skill map are paid once per invocation
whatever the cap is. Five slices per invocation now cost one delivery, at five
[GraphQL](https://graphql.org) round trips instead of one. Combined with the retry change, the reachable
ceiling moves from 200 files to 25,250.

`SKILL_SLICE_SIZE` itself stays at 50. It sits at the GraphQL batch ceiling
because a larger working set killed the isolate with `exceededMemory` on
2026-07-26, and that reasoning is unchanged.

**The remaining ceiling, made loud.** A chain is still finite, so a repository
past `MAX_INDEXABLE_SKILL_FILES` (20,000) now fails with the named reason
`repo_too_large_to_index` rather than dead-lettering silently on every hourly
tick. The reason joins `TERMINAL_DISCOVERY_REJECTION_REASONS`, so discovery stops
retrying it, and `repositoryIndexFailureMessage` renders it to a submitter as
"This repository is too large to index safely." Every known repository sits far
under the limit; the largest holds 6,341 skills.

### 2. A daily task was reported stale every single day

The nightly health email named `detect-star-surges` stale on both 2026-08-15 and
2026-08-16. The task was on time. Its cron is `30 4 * * *` and `sync_jobs`
records `last_status = 'ok'` at 2026-08-15T04:30Z, exactly on schedule.

`staleAfterSeconds` was a hand-kept list of cron prefixes: `*/5`, `*/6`,
`0 22 * * *`, `0 3 * * *`, and a 3-hour default for everything else. A daily task
whose cron was not one of the two literals in the list fell to the default, so
the check called it stale three hours after running. Any task added later with an
unlisted shape inherits the same false positive.

Fixed in this pass: the stale window is derived from the cron's actual period
(one full period plus half a period of slack, floored at 20 minutes). The two
shapes the list did cover land on the same 20 minutes and 36 hours as before.
Covered by `cronPeriodSeconds` unit cases and by a health-check case that fails
RED without the fix. Shipped in `23aecea`; the exit condition needs the next nightly run.

### 3. Rejected submissions are recorded as job failures

`repo-review-sync` recorded 61 `no_supported_skill_paths` and 12
`root_skill_unsupported` failures. These are terminal decisions, not faults: the
handler calls `ctx.fail(reason)`{lang="ts"} on `stats.status === 'rejected'` for a submitted
repository that has no supported SKILL.md.

They land in `failed_jobs`, so they inflated the "N jobs failed in 24 hours"
count that drives the health email to RED. A healthy day of correctly rejecting
unsuitable submissions read as an incident.

Fixed in this pass: the health check splits that table into faults and decisions,
applying the principle its own discovery-candidate alarm already states three
lines below. The reason list comes from the existing
`TERMINAL_DISCOVERY_REJECTION_REASONS`, bound as JSON so the values stay
parameters, plus the `skill_parse_rejected:` prefix that carries a path.
`failedJobs24h` counts faults only; `rejectedJobs24h` carries the decisions and
appears in both rendered reports, so the number stays visible rather than
disappearing. `ctx.fail` stays as it is, because the submission UI reads its
reason back out of `failed_jobs`. Shipped in `23aecea`; the exit condition needs the next nightly run.

## Deferred

**Replace the continuation release with a successor job.** This removes the
ceiling rather than raising it: retries would go back to meaning failure, and a
slice that made progress would not spend one. It is deliberately not done in this
pass, because it needs `repo_sync_progress` ownership handover, discovery claim
token inheritance, and a stable job id for `repository-index.ts` submission
tracking, and the failure has to propagate from a successor back to the tracked
root. The named `repo_too_large_to_index` rejection makes the remaining ceiling
visible in the meantime, which is what made the old one dangerous.

settled at 430 indexed skills and `posthog/posthog` at 276, both past the wall

progress rows. The newest dead-letter row predates the merge by over an hour.

The cleanest single number is the hourly batch: 6 failed jobs before the deploy,
0 after, on the same workload.

Two defects surfaced during delivery that this check-in had not caught. Required
CI typecheck failed on five `TS2345`s in `cronPeriodSeconds`, because
`noUncheckedIndexedAccess` makes a five-field destructure `string | undefined` and
the length guard does not narrow it; the local run had exited 0 through a pipe.
Required CI test then failed on `Hook timed out in 10000ms` across three arbitrary
files with zero assertion failures, and a different three locally on the same
commit. That is the flake class `vitest.config.ts` already documents: every worker
boots a full Nuxt environment, and capping the workers fixed the spawn failures
but left the per-file boot on vitest's 10-second default. `hookTimeout` raised to
30 seconds rather than re-running, which would only have moved the failure.

`x_ledger_stalled` investigation (5), the X projection decision (6), and the
usage token (7). Actions 1 and 2 are done. Action 4 needs the next nightly report.

## Corrections

The 2026-07-25 report first attributed the 4 remaining sync failures to repository renames, on the strength of an exact correlation: the 5 stuck repos were precisely the renamed ones. That was wrong. Worker logs showed `blob_batch_failed:502`, and direct measurement confirmed the cause was unchunked GraphQL batches. The renamed repos simply happen to be the largest. A supporting test (`getTree` returning 301 under curl) was also misleading, because it omitted `-L` while the Workers runtime follows redirects.

The 2026-08-03 report first blamed the embedding drift partly on head-of-line blocking, reasoning from the code that `embedding_attempts` is write-only, so failing skills would re-consume a slot every hour. The code reading is accurate and the conclusion was still wrong. Querying the table showed 480 completions in the last 24 hours against a 480 per day cap, with no attempt in any failed state for a week: no slot is being wasted. The 2,455 `rejected` rows that made the theory look plausible are all `malformed_acknowledgement` from 2026-07-23 and 2026-07-24, the incident already closed on 2026-07-25, and reading the row count without its date range turned closed history into an apparent live fault. Cumulative state tables need a recency filter before they can support any claim about today.
